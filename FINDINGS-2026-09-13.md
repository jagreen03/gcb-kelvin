**Status change from the prior assumption:** this repo's own README
and `ORANGE_TEAM.md` were written assuming no access to any relevant
simulator beyond what the existing evidence docs already used. That
assumption was checked, not just carried forward: **this session does
have real access to the exact WSL2 Ubuntu environment
`gcb-spec/docs/spice_setup.md` describes** — the real, already-built
`ngspice-44` + OSDI + `bsimcmg.osdi` + ASAP7 r1p7 toolchain genuinely
exists at `~/gcb_spice/tb/` and runs. **This does not mean Spectre
access exists** — it doesn't, and this finding does not change this
repo's core mandate (a commercial-simulator histogram). It does mean
this session could re-verify the toolchain's documented limits
directly, rather than only citing them, and — while doing that —
found one angle nobody had recorded before.

## 1. Re-confirmed, not assumed: `.noise` genuinely returns zero on the real BSIM-CMG device

Located the actual deck that tests this
(`~/gcb_spice/tb/_noise_cal.cir` — not tracked in any git repo, a
local WSL working file, per `spice_setup.md`'s own description of that
directory) and re-ran it against `7nm_tt_osdi.pm` + `bsimcmg.osdi`:

```
svg[80] = 0.000000e+00   frequency[80] = 1.000000e+06
svg[60] = 0.000000e+00   frequency[60] = 1.000000e+05
svg[100] = 0.000000e+00  frequency[100] = 1.000000e+07
```

**[M]easured-in-sim, confirmed**: input-referred noise spectral
density is exactly zero at every frequency checked, across 4 decades.
This matches `AGENT_02_ANALOG_EVALUATOR.md`'s documented finding
exactly — re-run, not re-derived, and it still fails the same way.

## 2. New finding: small-signal parameter extraction DOES work on the real device, even though internal noise synthesis doesn't

A separate, much simpler deck (`.op` only, no `.noise`) against the
same real `bsimcmg.osdi` model, same device (`nmos_lvt`, `nfin=8`,
`l=24n`), same bias point:

```
@n1[gm]  = 7.792610e-04   (S)
@n1[gds] = 3.372561e-05   (S)
@n1[cgg] = 4.278096e-16   (F)
```

**[M]easured-in-sim**: these are real small-signal operating-point
parameters, extracted directly from the real target device model — not
a BSIM4 surrogate gm-match. This had not been checked or recorded
anywhere in this program's existing evidence docs before this session
(confirmed by search — no prior mention of `@n1[gm]`-style extraction
in `gcb-papers/data/readout/spice/`).

## What this does and does not open up

**Does not close the core question.** No noise number for the full
comparator circuit was computed this session. `gm`/`gds` from one
isolated transistor at one bias point is not a noise result by itself.

**Opens one genuinely new, unbuilt path, not previously recorded**: a
classic manual SPICE noise technique — inject an explicit current
noise source at each transistor (spectral density `4·k·T·γ/gm`, using
the **real, device-extracted `gm`** above instead of a BSIM4
surrogate's gm-match), propagate it to the output via `.AC` small-
signal analysis (which also works fine on OSDI models — `.op` and
`.ac` are standard SPICE analyses, not noise-specific; only the
`.noise` directive itself appears to be the unsupported piece for this
OSDI integration), and integrate the output-referred spectral density
over the relevant bandwidth by hand. This would use the real target
device's real small-signal response end-to-end, closing the specific
gap the BSIM4-surrogate approach has (a *different* device's gm/gds,
not the real one) — without needing Spectre.

**What this does NOT solve on its own**: the full comparator is a
2-stage chopped/auto-zeroed preamp + StrongARM latch, not one
transistor — building a correct multi-transistor manual noise model
(noise source placement and correlation at every node, the chopper's
modulation of 1/f content, the latch's own regeneration noise) is a
real, substantial circuit-design task, not a SPICE scripting exercise,
and is **not attempted here**. The `γ` value itself is also still an
open question — `AGENT_02`'s own evidence notes ASAP7 ships no real
flicker/mismatch model, so any manual build still inherits an assumed
proxy for at least that term.

## Recommended next step, not started

A Research Scientist session with real analog-IC-noise-design
expertise (human or AI) building the manual multi-transistor
noise-injection model above, starting from the real `gm`/`gds` this
session confirmed extractable, would be a genuinely new attempt at
narrowing the ±16% band — distinct from, and not ruled out by, the
existing toolchain survey's conclusion (that survey ruled out
`.noise`/`trnoise` specifically, not manual small-signal noise
synthesis via `.op`+`.ac`). Not claimed to definitely work; claimed to
be a real, untried, technically sound angle worth a dedicated attempt.
